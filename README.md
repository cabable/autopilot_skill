# autopilot_skill
AutoPilot 踩坑固化清单 & 调参圣经（纯文字版）
Ⅰ. 架构地形图
本系统的调用链条为：用户界面层 → 屏幕截取层 → 图像处理与匹配层 → 执行控制层 → 操作系统输入模拟层 → 结果反馈闭环层。

致命的格式禁忌：屏幕截取层输出的色彩排列、图像处理层默认处理的色彩排列，以及界面层用来显示图片的色彩排列，三者互不相同。若不经显式转换直接混用，画面颜色将严重失真，表现为整体偏紫或偏绿，导致匹配完全失效。

Ⅱ. 硬核踩坑清单（按现场爆炸时间排序）
1. 界面组件初始化顺序陷阱
现象：程序报错提示“在窗口创建前尝试绘制图片”，即使绘制代码写在后面，只要窗口实例晚于图片加载动作，底层指针就会挂掉。

固化规则：必须严格按照“先创建窗口实例，再加载任何图片资源”的顺序执行。即使窗口默认是隐藏状态，也必须先让窗口对象活起来，之后才能进行图片读取和显示操作。任何在窗口实例化之前定义的图片相关全局缓存，都会引发崩溃。

2. 屏幕坐标系的物理像素偏差
现象：点击屏幕左上角精准，但点击屏幕中央区域时，鼠标总是落在目标点的左上方或右下方，偏差随距离增大。

根因：截屏库读取的是显示器物理像素，而操作系统的鼠标位置接口返回的是经过缩放比例处理后的逻辑像素。当系统缩放（如放大至125%或150%）开启时，两者坐标体系不一致。

固化规则：在截屏模块启动之前，必须主动向操作系统声明本程序已适配高DPI缩放，强制系统不再对坐标进行逻辑换算。此后所有坐标计算全部采用截屏库返回的原始物理数值，不再引入任何逻辑坐标转换公式。

3. 多尺度匹配中的尺度断档
现象：模板在缩小一点时能识别，放大一点时也能识别，偏偏在原始大小下匹配分数极低，导致漏检。

根因：为了节省计算资源，尺度生成策略的步长设置过大，导致从较小尺度跳变到较大尺度时，直接跳过了1.0倍原始比例，而模板图像在非整数倍缩放时会产生形变，原始比例反而是最精确的匹配基准。

固化规则：生成匹配尺度列表时，步长必须足够细密，且必须强制执行一项检查——无论步长如何计算，最终生成的尺度集合中，一定要显式包含1.0倍。绝对不能依赖浮点数运算自动覆盖。

4. 模板尺寸的生死铁律
为什么不能小于40像素？：尺寸过小的模板所包含的纹理特征点数量不足，在复杂背景中极易被噪点或类似色块干扰，误报率急剧升高。

为什么不能大于120像素？：过大的模板在进行平面旋转增强时，边缘会产生严重锯齿，且内部包含大量冗余背景，匹配时的滑动计算量成倍增长，严重影响实时性。

实战策略：若目标图标本身过小，不要直接拿它做模板。改为截取包含该图标在内的局部区域组合体，利用周围背景纹理辅助定位，匹配到该组合区域后，再通过相对偏移去点击中心目标。

5. 平面旋转增强的角度的硬上限
血泪教训：对模板进行旋转增强以应对界面轻微倾斜是必要操作，但旋转角度一旦超过某个阈值，匹配算法会对模板四个角落产生的黑色填充区域给予异常高分，导致错误定位。

固化规则：旋转增强的覆盖范围必须严格限定在正负15度以内，且步长不宜过密。绝对禁止使用30度或更大角度，除非目标本身具有明显的旋转对称性，否则宁可放弃匹配也不扩大角度范围。

6. 停止操作中的锁死纪律
现象：点击停止按钮后，界面立即无响应，鼠标转圈，最终只能强制结束进程。

根因：停止流程中存在层级调用冲突——外层流程先获取了资源锁，然后等待内层工作线程彻底结束；而内层工作线程在退出前也需要获取同一把资源锁来清理自身，于是双方互相等待，形成死锁。

固化规则：停止动作必须严格分三步走，不可打乱顺序——第一步，立刻修改运行状态标记（此操作不需要获取任何锁）；第二步，不带任何锁去等待工作线程自然苏醒并退出；第三步，确认线程已完全终止后，再单独获取锁去清理剩余残留数据。

7. 点击日志成功但游戏毫无反应的完整根因链（经典难题）
现象：日志明明打印了点击坐标，鼠标指针没动，或者游戏里的按钮没有被按下，但切换到记事本却能正常输入。

完整排查链条（按出现频率排序）：

第一层，窗口焦点失效：虽然找到了游戏窗口的句柄，但该窗口并未处于前台激活状态。向非前台窗口发送点击指令会被系统忽略，必须先将目标窗口强制提升至前台。

第二层，事件模式不匹配：某些游戏引擎（如基于特定框架开发的3D游戏）不监听常规的消息队列，而是直接轮询硬件输入状态。向窗口发送消息型点击无效，必须改用硬件层级的鼠标事件模拟。

第三层，按下与弹起的间隔过短：按下和弹起两个动作之间若没有足够的停留时间，游戏引擎会判定为无效抖动而非有效点击。必须在按下后加入短暂停顿再弹起。

第四层，坐标参考系错误：传给点击接口的坐标是截屏画面内的相对坐标，而非显示器上的绝对屏幕坐标。必须加上截屏区域左上角在屏幕上的实际偏移量，才能将鼠标移到正确位置。

Ⅲ. 高级机制：自学习闭环（经验回灌）
本系统最核心的防御逻辑在于“将模糊命中的案例固化为新的精准模板”。

运作流程：

图像匹配得分很高时，直接执行。

图像匹配得分处于中等模糊区间时，不盲目执行，而是借助上层逻辑（或人工预设规则）推断一个最可能的位置并执行试探性点击。

试探点击后，立即重新截取画面。若画面状态发生了预期变化（说明试探成功），则将该试探时刻的局部画面保存下来，并通过微小平移和轻微旋转生成若干变体，自动存入模板库。

下次启动时，模板库中便新增了针对该动态光照或轻微形变场景的专用参照，从而降低对通用特征的依赖。

Ⅴ. 终极工程防线（打包部署经验）
日志记录策略：不要只看数字日志。务必记录每一帧匹配中心点的坐标轨迹，当出现漂移时，回放这些点连成的运动路线，比阅读上千行日志定位问题要快得多。

内存占用监控：截屏操作返回的图像数据如果不主动释放，随着循环运行，内存占用会持续攀升。每次循环处理完毕后，必须主动丢弃当前图像数据，并在低帧率场景下定期触发内存整理。

异常情况兜底：当匹配失败、没有返回任何坐标时，绝不能直接中断流程或返回空值。必须返回一个包含“上次已知有效坐标”和“本次无效标记”的结构，由决策层决定是重试、暂停还是启动预测算法进行平滑过渡。

最终告诫：本手册所载内容均以实际运行中的崩溃、卡死、漂移和误触为代价换得。系统的长期稳定不依赖于任何高深理论，而取决于对这些底层细节的严格执行。若后续发现新的诡异现象，请在本手册末尾追加附录，以警后人。。

异常兜底：OpenCV 匹配失败返回空列表时，绝不要 return None，而是 return {"x": last_known_x, "y": last_known_y, "valid": False}，让控制层决定是重试还是使用卡尔曼滤波预测
